# M1-4 ｜ 系统调优：从"能跑"到"跑得稳、跑得快"

> **难度**：★★★★
> **综合考察**：全链路性能调优、QoS、执行器、故障诊断、技术写作
> **本题分值权重**：40（任务一 20 分 + 任务二 20 分）

---

## 场景

你的系统在实验室跑得好好的，**一上赛场就崩**：

- 图像话题丢帧
- 控制指令延迟飙升
- 端到端延迟累积到秒级

这是创意组比赛里**最致命的失败模式**。本题要求你直面它，给出工程化方案，
并**把你排查过程中真实踩到的坑记录下来**。

### 任务一：全链路性能调优

本目录给你**一条完整的图像链路**，**两端都要改**，分两个终端运行：

| 终端 | 文件 | 作用 |
| :-- | :-- | :-- |
| 终端1 | `camera_pub.py` | 发布 `/camera/image_raw`（640×480 bgr8，**目标 30 Hz**） |
| 终端2 | `image_proc.py` | 处理图像 → `/perception/result`（640×480 mono8）+ 发布 `/control/cmd`（**目标 20 Hz**） |

```bash
# 终端1
python3 camera_pub.py

# 终端2
python3 image_proc.py
```

**这是一道"全链路"题**：从**采集 → 发布 → 传输 → 接收 → 处理 → 发布结果**，
每一环都可能有瓶颈。**两端的代码都有问题，只改一端达不到达标线。**

**现状**（实测，3 次运行稳定）：

| 指标 | 现状 | 目标 |
| :-- | :-- | :-- |
| 输入 `/camera/image_raw` | **≈ 15.6 Hz**（看终端1 的 `[CAMERA]` 行） | **30 Hz** |
| 输出 `/perception/result` | **≈ 2.3 Hz** | **30 Hz** |
| 控制 `/control/cmd` | **≈ 2.3 Hz** | **20 Hz** |
| 端到端延迟 | **P50 ≈ 2386 ms / P95 ≈ 2443 ms** | **P95 < 200 ms** |

**你要做**：

1. 让**输入**恢复到 30 Hz（发布端的问题）
2. 让**输出**恢复到 30 Hz、**控制**恢复到 20 Hz（处理端的问题）
3. 使**端到端延迟 P95 < 200 ms**
4. 编写文档说明：**你牺牲了什么**（分辨率？丢帧换低延迟？算力？）

> ⚠️ **输入频率看终端1 自己打印的 `[CAMERA]` 行，不要用
> `ros2 topic hz /camera/image_raw`。**
>
> 原因：`ros2 topic hz` 自己也是一个订阅者，**它的启动/占用会与你的链路抢资源**，
> 读数偏低且不稳定。相机**自己数的帧**才是真值。

**怎么测**：

```bash
# 终端1：相机（它自己每 3 秒报一次频率 = 输入真实频率）
python3 camera_pub.py

# 终端2：处理链路
python3 image_proc.py

# 终端3：测量
ros2 topic hz /perception/result    # 输出：基线 ≈2.3Hz -> 应恢复 ≈30Hz
ros2 topic hz /control/cmd          # 控制：基线 ≈2.3Hz -> 应恢复 ≈20Hz
ros2 topic delay /perception/result # 端到端延迟
```

> `ros2 topic delay` 依赖**输出帧沿用输入帧的 `header.stamp`**。
> 这段约定已经写好在 `image_proc.on_image` 里，**不要改成重新打时间戳**，
> 否则测出来的延迟会假性归零。

**达标线**：输入 ≥ 30 Hz、输出 ≥ 30 Hz、控制 ≥ 20 Hz、
**P95 端到端延迟 < 200 ms**。

**在 README 里给出前后对比**：

| 版本 | 输入 | `/perception/result` | `/control/cmd` | P95 延迟 |
| :-- | :--: | :--: | :--: | :--: |
| 基线（`camera_pub.py` + `image_proc.py`） | ≈ 15.6 Hz | ≈ 2.3 Hz | ≈ 2.3 Hz | **≈ 2443 ms** |
| 你的版本 | ? | ? | ? | ? |

> **提示**：
> - **发布端**：为什么"造一帧图像"要花掉大半帧的时间预算？
> - **处理端**：延迟累积的根因往往**不是单帧算得慢**，而是**消息在队列里排队**。
>   看看订阅的 `depth` 设了多大（`image_proc.py` 的 `make_sub_qos`）。
> - 两端的瓶颈**互相独立**：只优化发布端，输出频率仍上不去；
>   只优化处理端，输入仍不到 30 Hz。

### 任务二：故障记录手册

**如实记录你在任务一优化过程中真实遇到的故障**，逐条写成报告。

一条合格的记录，必须包含这五项：

| 项 | 要求 |
| :-- | :-- |
| **① 现象** | 你观察到了什么？**贴命令与输出原文**（不是"报错了"，而是报错内容） |
| **② 定位过程** | 你怎么一步步缩小范围的？**试过哪些方法、哪些排除了** |
| **③ 根因** | 为什么会这样？**原理层面**的解释 |
| **④ 修复** | 改了哪里、怎么改的 |
| **⑤ 验证** | 改完用什么指标证明修好了（前后数字对比） |

**建议记录这些类别的问题**（做到哪条记哪条，**至少 4 条**）：

| 类别 | 典型现象 |
| :-- | :-- |
| 编译/环境 | `colcon build` 失败、`source` 后仍找不到包、Python 依赖冲突 |
| 话题/通信 | 话题名对不上、`ros2 topic hz` 收不到消息、**QoS 不兼容导致收不到数据** |
| 数据/编码 | 图像编码不符（`bgr8` vs `mono8`）、尺寸不匹配、`cv_bridge` 报错 |
| 性能/延迟 | 频率上不去、延迟越跑越高、CPU 打满、队列积压 |
| 并发/阻塞 | 控制回调被图像回调阻塞、死锁、单线程执行器卡住 |
| 时间戳/测量 | `ros2 topic delay` 读数异常、`header.stamp` 不一致 |

> ⚠️ **不要编造**。我们会在答辩时追问细节（"你当时敲的哪条命令？输出的哪一行让你
> 判断是这个原因？"）。**写 4 条真实的，远好过写 8 条编的。**
>
> "一次就过了、没遇到问题"**不是一个可接受的答案**——优化一条故意写坏的链路
> 不可能毫无波折。如果你真这么认为，说明你还没测到边界。

**写作建议**

- 每条记录用固定小标题，便于对照：`## 故障 N：<一句话现象>`
- **保留失败的尝试**：你试了 A 没用、B 没用、最后 C 成了——这个"排除过程"是加分项
- 用表格或代码块贴命令输出，别用截图（考官要能复制）

> 想练手的话，本目录的 `crash_worker.py` 会**真的触发一次段错误（SIGSEGV）**，
> 可以拿它当"故障样本"，练习"现象 → 定位 → 根因 → 修复 → 验证"这套流程：
>
> ```bash
> python3 crash_worker.py --fault-rate 1.0     # 立刻崩一次（exit code 139）
> ```
>
> 这是**可选**的练习，不是必须提交的内容。任务二的主体是**你自己踩的坑**。

## 接口契约（现场按此验收）

**任务一话题**（名字、类型必须一致）：

| 名称 | 类型 | 方向 |
| :-- | :-- | :-- |
| `/camera/image_raw` | `sensor_msgs/Image` | 输入（`camera_pub.py` 发布，640×480） |
| `/perception/result` | `sensor_msgs/Image` | **输出**（`mono8` 640×480） |
| `/control/cmd` | `geometry_msgs/Twist` | 控制指令（20 Hz） |

**关键约定**：

1. **输出帧的 `header.stamp` 必须沿用输入帧的 `stamp`**
   —— `ros2 topic delay` 与考官都靠它算端到端延迟。
   **重新打一个当前时间戳会让延迟假性归零**，这是作弊，直接判负。
2. **处理语义不变**：

   ```
   输入图 → 转灰度 → 提亮(+20) → 对比度增强((v-128)*3/2+128) → 输出灰度图
   ```

   允许改**实现方式**（向量化、换分辨率、改 QoS、改执行器），
   但**输出内容要与原语义一致**，不能直接输出原图来"达标"。
3. 输出尺寸 640×480、编码 `mono8`。
4. **输入图像的编码可以改**（例如 `bgr8` → `mono8` 省带宽），
   但 `image_proc.py` 必须能正确处理你发出来的编码。
5. **不允许"绕过题目"**：
   - 不能把相机定时器频率改低于 30 Hz（那是降低指标，不是优化）
   - 不能直接输出输入图来"达标"（必须真的做灰度+增强）
   - 不能靠 `header.stamp` 造假（见第 1 条）
   - 不能修改测量命令或换个话题名

**验收时考官会做**：

1. 跑基线（`camera_pub.py` + `image_proc.py`），确认**确实不达标**
   （输入 ≈15.6Hz / 输出 ≈2.3Hz / P95 ≈2443ms）
2. 跑你的版本，复核：**输入 ≥ 30 Hz、输出 ≥ 30 Hz、
   `/control/cmd` ≥ 20 Hz、P95 < 200 ms**
3. 检查你的输出图**确实做了灰度+增强**（不是原样转发）
4. 检查输出帧 `header.stamp` **确实沿用输入**（没有重新打时间戳）
5. **只改一端时，验证另一端确实成为瓶颈**（这是本题"全链路"的核心）
6. 读 `FAULTS.md`，**逐条追问细节**（见下）
7. 追问"你牺牲了什么"、以及某个改动**为什么**有效

> **任务二的追问方式**（关键——用来区分"真踩过坑"和"编的"）：
>
> 挑其中一条问："你当时敲的**具体哪条命令**？输出的**哪一行**让你判断是这个原因？"
> 再往下问一层："如果当时那条命令输出是这样（给个变体），你会怎么想？"
>
> 真的踩过坑的人，能说出细节和当时的困惑；编的人会在第二层露馅。

- 先**量化**再动手：不测就优化是瞎猜

  看看订阅队列深度（`depth`）设了多大
- 卡住时**记下来**：命令、输出、你的猜测、后来发现对不对——
  这就是任务二的素材，别等做完了再凭记忆补
- `ulimit -c unlimited` 可以打开 core dump，配合 `dmesg` 定位崩溃
