# 智能车创意组考核方案

> - 结构：**1 个基础模块（必做）+ 1 个专业模块（任选必做）+ n 个拓展模块（任选）**
> - 题量：7 个模块 × 4 题 = **28 题**，模块内难度递增
> - 形式：作业（在家完成，交代码+文档+记录）+ 现场考核/答辩（到场地跑，接受追问）

## 1. 总则与通用规则

### 1.1 考核目的

考核是为了选拔具有 **自学，独立解决问题** 能力的同学，是能够在 **一堆报错中精确定位问题所在，懂得提问，能和队友协作** 的同学。

### 1.2 三条铁律

1. **严禁隐瞒 AI 使用**
    - 使用了 AI 后，需要在相关文档中指出哪里/什么模块使用 AI 编写，代码有没有经过验证，代码有没有仔细研究。
2. **严禁一次提交 GIT**
    - 代码需要有多次有意义的 GIT 提交，而不是最后一次性提交，保证过程的记录
3. **严禁买卖，剽窃代码**
    - 可以向他人请教，可以参考别人的代码，但是 **严禁代码买卖，严禁剽窃他人的代码。被发现直接滚蛋** 。

## 2. 考核架构总览

考核题目分为 **多个模块 M0 - M6** ，每个模块下设 **四个问题** ，每个问题 **难度递增** 。

每个模块共 100 分，题目分值按难度递增 10, 20, 30, 40；每个题目按 100 计，然后折算为模块分值。例如，M0-1 得分 80 分，则计入 M0 总分 8 分，M0-3 得分 90 分，则计入 M0 总分 27。

### 2.1 选做规则 1 + 1 + n

|     位置    | 内容 | 完成要求 | 考察目的 |
| :---------: | :--: | :--: | :--: |
| 第 1 个 "1" | **M0 基础与自学能力** | 所有人必做，**4 题全交** | 编程能力、电脑与环境使用、自学能力。 |
| 第 2 个 "1" | **从 M1–M5 中任选 1 个** | 该模块 **4 题全做** | 确立主攻方向，考察专业深度 |
| "n"         | 从剩余 M1 - M5 个模块中任选 n 个（可以不选，**建议 1–2 个**） | 每选一个模块，至少任意完成 **2 题**，且**至少包含该模块的第 3 题** | 考察综合广度与团队补位能力 |


> **为什么 n 模块至少包含第 3 题？**
> 防止靠刷前两道简单题凑模块数量。第 3, 4 题是模块的难题，做不出来也能拿分（看你卡在哪、怎么求助），才能学到真正有用的。

### 2.2 单题评分维度

| 维度 | 分值 | 看什么 |
| :-- | :--: | :-- |
| 任务完成 | 40 | 需求点是否逐条覆盖，能不能真跑起来，边界情况处理了吗 |
| 过程证据 | 20 | Git 提交密度与质量、踩坑记录是否可信、时间投入是否合理 |
| 工程规范 | 10 | 目录结构、命名、README、参数是否硬编码、能否一键复现 |
| 权衡与判断 | 10 | 是否说清"我为什么这么做、放弃了什么、什么情况下这个方案会失效" |
| 答辩 | 20 | 讲不讲得清、能不能迁移到新场景、知不知道自己不知道什么 |

### 2.3 总要求

- M0 总分不低于 60 分，专业模块不低于 60 分
- 个人总分按模块累计，如 90 + 80 (+ 50) = 170 (220) 分

> 理论上我们一轮不淘汰，分数仅用于二轮找队友的凭证，但是如果及格分都到不了，建议多沉淀沉淀

### M0 工程基础

#### M0-1 | 从零搭建开发环境

> - 难度 ★

**场景**：你刚进车队，学长丢给你一句话：“装Ubuntu和ROS及相应的开发环境，速交。”——所有故事的起点。

**任务**：

1. 在物理机 / WSL2 / 虚拟机（三选一）上装好 Ubuntu 22.04 + ROS2 Humble + Python虚拟环境（uv或conda）+ C/CPP + VS Code（含必要开发插件） + Git
2. 写一份 README——简写通过什么方法/查阅什么资料完成什么任务，重点写 “本机踩坑实录” ，例如装系统时遇到什么问题，如何解决等等

4. 学会远程登陆，操控远程电脑（服务器、开发板等）

**完成判断**：考核时在本机环境下跑通提供的脚本（现场提供），允许修复，直到跑通。远程登陆到开发板，完成 M0-2。

> **注意**：考核对于每一模块没有时间限制，但是考核时间过了就截止。


#### M0-2 | 首个代码工具

> - 难度 ★★ 
> - 综合考察：编程基础

**场景**：你写了一段能跑的代码，但队友看不懂、没法改、不知道版本。能跑 ≠ 工程能接受。这一题教你一个程序员的基本修养——避免前期代码埋雷，后期排查到头秃。

**任务**：

你拿到一个“祖传”的 Python 脚本（我们提供，写得很烂）——它功能是读取一个 yaml 文件，获取具体任务要求，然后读取一个 csv 文件获取数据，然后计算两列数据的相关系数，并打印结果。但它存在以下问题：

- 没有函数封装，全是全局变量
- 没有异常处理（文件不存在直接崩溃）
- 没有 `if __name__ == "__main__"` 保护
- 计算相关系数的公式写错了（或者用了不稳定的数值方法）
- 没有任何注释和文档

请你完成以下重构：

1. Git 仓库初始化：建一个 git 仓库，至少进行 5 次有意义的提交。提交信息必须符合规范
2. 代码重构：
    - 将核心计算封装成函数
    - 添加完善的异常处理（文件不存在、空文件、列名不匹配、除零错误）
    - 修复算法错误，确保计算结果与 numpy.corrcoef 一致（允许引入 numpy 做验证，但核心计算逻辑要手写）
3. 单元测试：写一个简单的 test.py，用已知数据（例如 [1,2,3] 和 [2,4,6] 相关系数应为 1.0）验证你的函数。
4. README：写清楚如何运行、输入文件格式要求、输出结果的含义。

**完成判断**：在现场运行一组全新的 yaml + csv ，运行成功则任务完成。

> **注意**：此题如果使用 AI 帮你写代码，必须在 README 中如实说明**哪些部分用了 AI、你是否逐行研究并验证过**。现场答辩会围绕这部分重点追问。

#### M0-3 | 代码排查

> - 难度 ★★★ 
> - 综合考察：Debug能力

**场景**：上一届学长解脱前留下了一个“能用”的Python脚本，说是“处理一下传感器数据就能用”。但当你真正运行它时，发现各种报错、各种诡异的结果。没人给你讲逻辑，你只有代码和一行注释。—— ~~学长不乘，但是你抓不到了。~~ 事实是，你写代码从第一行开始就一直报错，或者你费劲千辛万苦写好的一大段代码，结果跑不动。

**任务**：

我们为你提供一份存在8处典型缺陷的Python脚本 `sensor_analyzer.py`，以及一份模拟的 `sensor_data.csv` 数据文件。

脚本的“原本意图”：读取CSV文件中两列数据（time和value），计算这些数值的平均值、标准差，并剔除其中的离群值（Outliers，超过2倍标准差），最后将清洗后的数据保存为 cleaned_data.csv，并打印一份统计摘要。

1. 请你修复代码，并完成原本的脚本意图。
2. Git 提交
3. 编写 README 文档——问题报告，哪里有问题，哪里怎么解决

**完成判断**：代码能够成功运行现场提供的 csv 文件。

> **注意**：此题如果使用 AI 帮你写代码，必须在问题报告中如实说明**哪些部分用了 AI、你是否逐行研究并验证过**。现场答辩会围绕这部分重点追问。

#### M0-4 ｜ Mini 项目实战

> - 难度 ★★★★
> - 综合考察：结构化项目管理能力

**场景**：比赛时，车要按顺序做多个任务（比如先巡线、再避障、最后停车）。你需要写一个命令行下的任务调度模拟器，把“任务状态管理”和“时间监控”抽象成代码。不依赖任何 ROS 或 GUI，全在终端运行。

**任务**：

实现一个名为 TaskScheduler 的 Python 程序，满足以下需求：

1. **配置加载**：读取一个 tasks.yaml（或 tasks.json）文件，里面定义了 5~8 个任务。每个任务包含：
    - name: "Navigate"
    - duration: 2.5 （预期耗时，单位秒）
    - success_rate: 0.8 （模拟成功率）
    - dependencies: ["Init"] （依赖的前置任务列表）
2. **核心调度逻辑**：
    - 按依赖顺序执行任务（拓扑排序）。
    - 每个任务模拟执行时，根据 `success_rate` 随机判定成功或失败。
    - 如果任务失败，最多重试 2 次，若仍失败则跳过该任务（记录为 SKIPPED），继续执行后续不依赖它的任务。
    - 时间会计：程序运行开始时记录真实时间，每执行一个任务，sleep(duration) 模拟耗时，并累加总耗时。如果总耗时超过用户设定的 --timeout 15（秒），立即终止所有任务并输出 TIMEOUT。
3. 日志与输出：
    - 控制台必须实时彩色输出（绿色 SUCCESS、红色 FAILED、黄色 RETRY、蓝色 SKIPPED）。
    - 程序运行结束后，生成一个 report.yaml/report.json，包含：每个任务的最终状态、总耗时、超时与否。
4. 工程规范（综合考察）：
    - 必须使用虚拟环境（证明你会用 M0-1 装的环境）。
    - 提供 requirements.txt。
    - 必须写完整的 README.md，包含参数说明和 3 个运行示例。

**完成判断**：代码能够成功运行现场给出的 yaml/json

> **注意**：无论后续任务是否要求，都需要编写文档，若有编写要求，则按照要求来。

#### M1-1 ｜ 三节点链路 + 动态配参

> - 难度 ★
> - 综合考察：ROS 基础，各大通信方式


**任务**：实现一个“虚拟超声波测距”链路。

1. **节点A（发布者——模拟传感器）**：以10Hz发布一个自定义 `SensorData.msg` ，包含：
    - `float32 distance` - 模拟超声波的距离
    - `string unit` - 模拟超声波距离的单位
    - `builtin_interfaces/Time stamp` - 模拟消息生成时间
    - `uint8 status` - 模拟传感器状态，0=正常，1=超出量程，2=传感器错误
2. **节点B（处理者——数据滤波与转换）**：
    - 订阅该话题，并用一阶低通滤波平滑数据。
    - 滤波系数 $\alpha$ 必须做成ROS参数（能用`ros2 param set`在运行时动态修改，并在终端看到效果）。
    - 滤除 `status != 0` 的无效数据（不参与滤波，但要打印警告日志）
    - 将滤波后的结果通过另一个话题 `/processed_distance` 发布，消息类型使用ROS2标准消息 `std_msgs/Float32`
3. **节点C（执行者——结果响应）**：
    - 订阅处理后的结果
    - 当距离 < 0.3m时，调用一个自定义服务 `TriggerAlarm.srv` 触发“报警”，并打印日志。
    - 服务端可以简单地打印 `[ALARM] 距离过近！` 并返回成功。
    - 正确处理服务超时（若服务端1秒无响应，打印 `[WARN] 报警服务超时`）。

**完成判断**：Py/C++任选，跑通代码。能够看到发布的话题，处理的结果与实时日志。

#### M1-2 ｜ Launch编排：从“一个个敲命令”到“一键启动”

> - 难度 ★★
> - 综合考察：Launch管理节点

**任务**：

基于M1-1的三个节点（或重新写一套新的三个节点），完成以下Launch工程化改造：

1. **Python Launch文件**：写一个 `bringup.launch.py`，一键启动全部3个节点。
    - 使用 Python 格式 编写Launch文件（不允许 `XML/YAML`）。
    - Launch文件必须支持命令行传参：`ros2 launch my_pkg bringup.launch.py namespace:=my_robot`。
    - 所有节点必须运行在同一个命名空间下（由命令行参数 `namespace` 控制）。
    - 每个节点的名称必须显式指定（不依赖默认名称）。
2. **参数管理**：
    - 节点B的滤波窗口大小、节点C的报警阈值，必须从 `YAML` 参数文件 加载。
    - 参数文件路径也必须是Launch的可配置参数（`params_file:=/path/to/params.yaml`）。
    - 在Launch中演示参数覆盖：同一个参数在不同命名空间下可以有不同值（例如 robot1 的阈值为0.3，robot2 的阈值为0.5）。

3. **多组实例**：用同一个Launch文件，启动 **两组完全独立** 的节点实例（不同命名空间）：
    - 第一组：`namespace:=robot1`，报警阈值0.3m
    - 第二组：`namespace:=robot2`，报警阈值0.5m
    - 两组实例必须同时运行，互不干扰（话题名自动隔离）。

4. **事件与依赖**：在Launch中实现节点启动顺序控制——节点C必须在节点B完全启动后才启动（不能同时启动导致服务调用失败）。
5. **错误处理**：如果 `YAML` 参数文件不存在，Launch要给出清晰的错误提示，而不是Python栈回溯。

**完成判断**：现场演示一键启动脚本，终端中正确输出相应日志，并且能够清楚地区分两组命名空间。

#### M1-3 ｜ 时间与坐标：让两个传感器“说到一起去”

> - 难度 ★★★
> - 综合考察：多传感器数据处理

**场景**：车上有一个摄像头和一个激光雷达，它们安装位置不同、采样频率不同、时间戳也不同。你要做的是——把激光雷达的点投影到摄像头图像上，让它们“看到同一个世界”。这是多传感器融合的基石。

**任务**：

使用离线合成的 rosbag（含 /scan 和 /camera/image_raw 话题；由 M1-3 目录下的 `make_bag.py` 生成，也可用你自己的公开数据），在离线回放中完成以下任务：

1. **TF2坐标树**：
    - 建立并发布以下静态TF变换：
    - map → odom → base_link → laser_link
    - base_link → camera_link
2. **时间同步**：
    - 使用 `message_filters.TimeSynchronizer`（或 `ApproximateTimeSynchronizer`）同步 `/scan` 和 `/camera/image_raw`。
3. **点云投影**：
    - 将同步后的激光雷达点云（`/scan` 是2D激光，只有 x 和 y，z=0），投影到图像平面上。
    - 每个激光点按距离着色（近处红色，远处蓝色）画在图像上。
    - 输出至少 3张 不同时刻的投影效果图。
4. **时钟处理**：
    - 回放bag时，必须正确处理 use_sim_time 参数。
    - 演示切换 use_sim_time（true ↔ false）时，系统行为会发生什么变化（录屏记录）。

**完成判断**：现场展示实时演示图像。

#### M1-4 ｜ 系统调优：从"能跑"到"跑得稳、跑得快"

> - 难度 ★★★★
> - 综合考察：全链路性能调优、QoS、执行器、故障诊断、技术写作

**场景**：你的系统在实验室跑得好好的，一上赛场就崩——图像话题丢帧、控制指令延迟飙升、端到端延迟累积到秒级。这是创意组比赛里最致命的失败模式。本题要求你直面它，给出工程化方案，并把你排查过程中真实踩到的坑记录下来。

**任务**（本题目分两部分，都要做）：

| 部分 | 内容 |
| :-- | :-- |
| **任务一** | 把一条**全链路都很慢**的图像链路优化到达标线 |
| **任务二** | **故障记录手册**：记录你在任务一优化过程中真实遇到的故障、排查过程与修复方法 |

1. **任务一：全链路性能调优**：给你一条**两端都有缺陷**的图像链路，分两个终端运行：
    - 终端1 `camera_pub.py`：发布 `/camera/image_raw`（640×480，**目标 30 Hz**，实际跑不到）
    - 终端2 `image_proc.py`：处理图像 → `/perception/result` + 发布 `/control/cmd`（**目标 20 Hz**）

    现状（实测）：输入 ≈15.6 Hz、输出 ≈2.3 Hz、控制 ≈2.3 Hz、端到端延迟 P50 ≈ 2.4 s。
    **两端缺陷互相独立，只改一端无法达标**。

    请你改造代码使其全部达标：**输入 ≥ 30 Hz、输出 ≥ 30 Hz、控制 ≥ 20 Hz、
    端到端延迟 P95 < 200 ms**。并编写文档说明：写清楚你牺牲了什么（分辨率？延迟换吞吐？CPU占用？）。

2. **任务二：故障记录手册**：把你在任务一优化过程中**真实踩到的故障**逐条记录成 `FAULTS.md`，每条包含五要素：
    - ① 现象（**命令与输出原文**，不是"报错了"）

#### M5-1 ｜ 任务状态机：把比赛任务「串起来、跑通、可调试」
> - 难度 ★
> - 综合考察：状态机建模、节点封装、上下文流转、契约测试、YAML 编排

**任务**：

比赛任务 = 「等待发车口令 → 巡线到识别区 → 识别二维码/图文 → 导航到抓取区 → 视觉伺服抓取 → 避障搬运到放置区 → 定点放置 → 导航回充电桩」。每步是独立 ROS2 Action/Service。你要写一个 **纯 Python 状态机**，把它们按顺序/并发/重试/超时/降级串起来，**不依赖 BehaviorTree.CPP、不依赖 Groot2**，终端跑、日志清、单测全。


1. **状态机框架（< 200 行核心代码）**：
   - 状态：`IDLE` `RUNNING` `SUCCESS` `FAILED` `SKIPPED` `RETRYING`
   - 转移：成功→下一状态、失败→重试(可配置次数/间隔)→仍失败→走降级分支/标记 SKIPPED、超时→走降级分支
   - 支持**并发分支**（`Parallel`：所有子状态成功才算成功、任一失败按策略处理）
   - **上下文对象**：`TaskContext`（任务 ID、截止时间、共享数据字典、重试预算、降级标记、元数据）

2. **5 个标准任务节点（Mock 实现，继承基类 `TaskNode`，接口固定）**：
   - `WaitForTrigger`：等 `/referee/start_cmd` 或键盘空格，超时 30s
   - `NavigateTo`：调用 `/navigate_to_pose` Action，传入目标位姿，成功/失败/取消语义完整
   - `DetectTarget`：订阅 `/perception/targets`，等待目标类别/置信度达标，输出到上下文 `target_pose` `target_id`
   - `ExecuteGrasp`：调用 `/manipulation/grasp` Action，输入上下文 `grasp_pose` `grasp_type`，输出 `grasp_result` `object_pose`
   - `SpeakTTS`：调用 `/tts/speak` Service，播报状态/异常/求助

3. **任务编排 DSL（YAML）**：
   ```yaml
   tasks:
     - name: wait_start
       type: WaitForTrigger
       timeout: 30
     - name: navigate_to_scan
       type: NavigateTo
       pose: !include poses/scan_zone.yaml
       retry: 2
       fallback: wait_start
     - name: detect_qr
       type: DetectTarget
       target_class: "qrcode"
       min_confidence: 0.7
       timeout: 15
       fallback: navigate_to_scan
     - name: navigate_to_grasp
       type: NavigateTo
       pose_from_context: target_pose
       retry: 1
     - name: grasp
       type: ExecuteGrasp
       grasp_type: "top_down"
       retry: 2
       fallback: navigate_to_grasp
     - name: navigate_to_place
       type: NavigateTo
       pose: !include poses/place_zone.yaml
     - name: speak_done
       type: SpeakTTS
       text: "任务完成"
   ```

4. **运行时表现**：
   - 终端**实时彩色日志**（状态转移/上下文变更/重试/降级/超时）
   - 生成 `task_report.json`：每状态耗时/结果/重试次数/降级标记/最终上下文
   - **单测覆盖**：每个 `TaskNode` 至少 3 个用例（正常/超时/失败→重试/降级），Mock ROS2 依赖

**完成判断**：现场给一份**未见过的任务 YAML**（含并发分支、重试、降级），仿真环境下：
- `python run_task.py task_demo.yaml` 一键跑通
- 终端日志清晰显示每状态进出、上下文关键字段
- `task_report.json` 字段完整、耗时合理
- 单测 `pytest tests/` 全绿

#### M6-1 ｜ 从模型到板端：ONNX 导出 + 基础部署
> - 难度 ★

   - **后量化（PTQ）**：
     - 收集校准数据集（100-500 张真实赛道图像），构建 `calib_dataset/`
     - FP32 模型 → INT8 量化：`torch.quantization.quantize_dynamic` / `ONNX Runtime Quantization`（`opt_qdq`）/ `RKNN-Toolkit2` / `TensorRT INT8`
     - 三种量化方案分别跑通（动态量化 / 静态量化 / QAT 可选）
   - **精度回退分析**（逐层/逐算子）：
     - 对比量化前后每层输出的 CosSim / KL 散度
     - 定位**精度损失最大的层**，记录原因（算子不支持量化 / 校准数据不足 / 数值范围异常）
     - 输出 `quant_analysis.csv` + 可视化热力图

2. **硬件加速器部署**：
   - **Jetson**：`torch2trt` / `polygraphy` 将 ONNX 转为 TensorRT Engine (`best.engine`)，`trtexec --int8 --calib=calib/`
   - **地平线 RDK**：`hb_mapper` / `hbdk` 编译为 BPU 模型 (`best.bpu`)，`hb_board` 推理
   - **通用**：`NCNN` / `MNN` 部署作为 fallback
   - 每种后端输出：`best_<backend>.engine`/`.bpu`/`.bin` + `deploy_config_<backend>.yaml`

3. **性能对比表**：

   | 模型/后端 | 精度 mAP | FPS (板端) | 推理延迟 P95 | 显存占用 | 文件大小 | 功耗 |
   |-----------|----------|------------|--------------|----------|----------|------|
   | FP32 ONNX (CPU) | 0.85 | 8 | 125ms | 1.2GB | 28MB | 15W |
   | INT8 ONNX (CPU) | 0.84 | 22 | 45ms | 0.4GB | 7MB | 12W |
   | INT8 TensorRT (GPU) | 0.84 | 45 | 22ms | 0.6GB | 8MB | 18W |
   | INT8 RKNN (NPU) | 0.83 | 52 | 19ms | 0.3GB | 6MB | 8W |

   - 实测数据必须来自板端 `tegrastats`/`rknn_profiler`/`onnxruntime` profiling
   - **精度损失 < 2%**、**FPS ≥ 2× FP32** 才算达标

4. **量化后处理**：
   - 如果 mAP 下降 > 2%，必须做**QAT 微调**（1-2 个 epoch）并记录微调数据/超参/结果
   - 如果某算子不支持量化（如自定义 NMS），实现**混合精度**：量化主体 + 保留 FP32 算子

**完成判断**：现场给一台开发板 + 100 张未见过的赛道图像（测试集）：
- 量化模型 mAP 与 FP32 对比：下降 < 2%（逐类详细报告）
- 板端实测 FPS ≥ 30（任一旁即可），延迟 P95 < 35ms
- `quant_analysis.csv` + `benchmark_multi_backend.yaml` 完整
- 演示：板端实时检测 60 秒不崩溃，量化后画面与 FP32 基本一致

#### M6-3 ｜ ORT 会话调优与 CUDA Graph：推理引擎深度优化
> - 难度 ★★★
> - 综合考察：推理引擎配置、执行器选择、CUDA Graph 捕获、延迟确定性

**场景**：M6-2 的 INT8 模型，板子上跑起来 **22 FPS**，但比赛要求 **≥ 30 FPS**，且**每帧延迟必须稳定在 35ms 以内**（不能忽快忽慢，否则导航会跟丢）。问题出在 ONNX Runtime 的默认配置没调优——执行器选错了、Graph Optimization 关闭了、CUDA 流没配对、内存池浪费了大量碎片。

**任务**：

1. **执行器对比与选择**：
   - 同一 INT8 ONNX 模型分别用 **CUDAExecutionProvider** / **TensorRTExecutionProvider** / **CPUExecutionProvider** 跑
   - 记录每种 EP 的：FPS / P50延迟 / P95延迟 / P99延迟 / GPU利用率 / 显存
   - **重点对比 TensorRT EP vs CUDA EP**：TensorRT 有时反而慢（kernel 自动调优未完成），需要通过 `trt::ExecutionContext` 手动设置 `precision_mode` / `tactic_sources`
   - 输出 `ep_comparison.yaml`：含所有指标 + 推荐配置

2. **会话配置深度调优**：
   - `SessionOptions` 关键参数逐一调整，记录对延迟的影响：
     - `graph_optimization_level`：ORT_DISABLE → ORT_ENABLE_BASIC → ORT_ENABLE_EXTENDED
     - `intra_op_num_threads` / `inter_op_num_threads`
     - `enable_mem_pattern` / `enable_cpu_mem_arena`
     - `execution_mode`：ORT_SEQUENTIAL vs ORT_PARALLEL
     - `cuda_stream_id` / `cuda_graph_capture_id`（CUDA Graph 捕获消除 kernel launch 开销）
   - **逐参数实验**：每次只改一个参数，跑 100 帧看延迟变化
   - 输出 `session_tuning.csv`：每个参数组合的性能数据

3. **CUDA Graph 捕获（确定性延迟）**：
   - 用 `CUDA Graph` 捕获推理流程（预处理→推理→后处理）的 kernel 启动序列
   - 捕获后**直接执行 graph**，消除 kernel launch 开销（约 5-10μs/次）
   - 验证：P99 延迟从 **50ms 降到 35ms 以内**，延迟波动 < 5%
   - 注意：输入尺寸固定后才能捕获图，需要确认模型支持固定分辨率

4. **延迟稳定性测试**：
   - 跑 **1000 帧连续推理**，输出延迟分布直方图
   - 要求：**P95 < 35ms**、**P99 < 50ms**、**最大单帧延迟 < 80ms**
   - 对比调优前后的延迟分布：调优前抖动大（15-80ms），调优后稳定（30-35ms）
   - 输出 `latency_stability.pdf`：直方图 + 累积分布曲线 + 统计表

**完成判断**：现场给一台开发板 + 量化后的 INT8 ONNX 模型：
- 原始 ORT 默认配置：FPS ~22，P95 ~50ms
- 调优后（推荐 EP + 会话配置 + CUDA Graph）：**FPS ≥ 30，P95 < 35ms，P99 < 50ms**
- `ep_comparison.yaml` + `session_tuning.csv` + `latency_stability.pdf` 完整
- 现场演示：1000 帧连续推理，延迟稳定无大抖动，180 秒比赛不崩溃

#### M6-4 ｜ 多线程推理管线：重叠预处理·推理·后处理
> - 难度 ★★★★
> - 综合考察：多线程/异步编程、生产者-消费者模式、零拷贝内存、共享资源管理

**场景**：板子上只跑**一个模型**，但传感器 30Hz 不断喂帧。CPU 预处理一帧要 20ms，模型推理 33ms，后处理 10ms——串行的话每秒最多跑 **17 FPS**。你需要用**多线程**让预处理、推理、后处理**流水线并行**，像工厂流水线一样"前一帧推理时后一帧在预处理"，整体吞吐突破 **30 FPS**。

**任务**：

1. **流水线架构设计**：
   - 三级流水线，每个阶段一个独立线程 + 一个任务队列：
     - **Preprocess 线程**：读取原始帧 → 缩放/归一化/通道变换 → 放入 `queue_pre`
     - **Inference 线程**：从 `queue_pre` 取出 → 模型推理 → 放入 `queue_post`
     - **Postprocess 线程**：从 `queue_post` 取出 → NMS/解码/绘制 → 发布检测结果
   - 三线程**异步运行**，各阶段独立吞吐，通过**有界队列**（`queue.Queue(maxsize=4)`）解耦
   - 实现**背压**：`queue_pre` 满 → Preprocess 线程等待（不丢帧、不爆内存）

2. **零拷贝内存管理**：
   - 原始帧（`np.ndarray`）在 Preprocess 和 Inference 线程间**共享内存**（`multiprocessing.shared_memory` 或 `cv2.UMat`/`torch.from_numpy` 共享底层 buffer）
   - **禁止**帧数据在队列中反复拷贝（序列化→反序列化）
   - 使用**双缓冲**（Double Buffering）：Preprocess 写完 Buffer A → Inference 读 Buffer A + 写 Buffer B → Postprocess 读 Buffer B（时间重叠）
   - 内存占用实测：4 路视频流并发时总内存 < 300MB（vs 串行 800MB）

3. **线程安全与资源竞争**：
   - 模型推理引擎（TensorRT Session/RKNN Handle）**线程安全**设计：单例 + 锁/无锁队列
   - CUDA 流（`cuda.Stream`）并发：Preprocess 在 Stream A、Inference 在 Stream B，**GPU 内核并发执行**
   - 线程同步：`threading.Event` / `queue.Queue` / `condition variable`，无死锁、无竞态
   - 每个线程编写**单元测试**（Mock 数据源/Mock 推理引擎）

4. **性能验证**：
   - 同一模型同一板子，对比：
     - **单线程串行**：Preprocess→Infer→Postprocess 全写完再读下一帧
     - **双线程**（Preprocess+Infer 并行）
     - **三线程管线**（全部并行）
   - 记录每种方案的：**FPS / P95 延迟 / 内存占用 / CPU 各核利用率 / GPU 利用率**
   - 必须跑满 **3 分钟**稳定运行，验证无内存泄漏（RSS 波动 < 50MB）
   - 输出 `pipeline_benchmark.yaml`：三方案对比 + 加速比 + 瓶颈分析

**完成判断**：现场给一台开发板 + 一个摄像头（30fps）：
- 三线程管线跑通，`python pipeline.py --threads 3 --stream camera` 实时输出检测框
- FPS **≥ 30**（vs 单线程 17），P95 延迟 < 40ms
- 3 分钟稳定运行无崩溃/无内存泄漏
- `pipeline_benchmark.yaml` 三方案对比完整，加速比 ≥ 1.6×
- 单元测试 `pytest tests/` 全绿，覆盖线程安全/背压/异常恢复
