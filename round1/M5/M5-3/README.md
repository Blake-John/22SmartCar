# M5-3 ｜ 裁判/交互/远程干预一体化终端：现场「人机协作」唯一入口

> **难度**：★★★
> **综合考察**：裁判协议解析、多模态交互、参数/模型热切、安全兜底、审计日志
> **本题分值权重**：30
> **题目来源**：`创意组一轮考核.md` §M5-3
> **形式**：纯软件（主机侧）。现场带代码，**考官会按完整赛制流程演练**

---

## 0. 这道题在考什么

比赛现场有个硬约束（题面原文）：

> **裁判指令通过话题/串口下发；队员只能通过上位机终端操作；
> 不许开新终端、不许 ssh、不许改代码。**

也就是说：**终端就是你唯一的手**。它必须把下面这些**集成在一个界面**里：

- 收裁判指令、确认、显示倒计时
- 语音/按键/触屏触发任务
- 远程切模型/切参数/切场景（**不重启节点**）
- 紧急停车 / 求助 / 复位
- **所有操作留审计日志**（赛后能当申诉证据）

考四件事：

1. **协议对接**：裁判协议解析正确，倒计时/阶段/犯规实时同步
2. **热切能力**：切参数/模型**不重启**，且切换**被记录**
3. **安全兜底**：急停要真的停，且**各层都能兜住**
4. **可追溯**：审计日志能追到"谁在什么时候改了什么"

> **最容易翻车的地方**：急停只发了一条 `/cmd_vel` 零速度就完了。
> 底盘可能因为控制器超时、或另一路指令源覆盖而继续走——
> **急停必须是多层的**（见 §2.3）。

## 1. 硬性要求

| # | 要求 | 说明 |
| :-- | :-- | :-- |
| 1 | **裁判适配器** | 订阅 `/referee/cmd`，发布 `/referee/status`；支持**模拟模式**（键盘 `S`/`P`/`R`/`E`） |
| 2 | **协议覆盖** | `START` `PAUSE` `RESUME` `STOP` `PENALTY` `SCORE_QUERY`；状态回报 `READY` `RUNNING` `PAUSED` `STOPPED` `FAULT` |
| 3 | **终端跑在主机上** | 小车端**只增加一个 `/emergency_stop` 订阅者**，**零额外进程** |
| 4 | **任务控制** | 启动 / 暂停 / 继续 / 跳过当前节点 / **紧急停车** |
| 5 | **参数与模型热切** | 切 `scene_*.yaml`、切模型、调滑块；**不重启节点**，且**每次自动记录** |
| 6 | **多模态触发** | 语音唤醒词（离线）+ 物理按键，映射到相同动作 |
| 7 | **求助/复位** | 求助裁判、**软复位**（不重启节点）、**硬复位**（比赛中禁用） |
| 8 | **审计日志** | 所有操作写 `audit_log_<date>.jsonl`，**只追加 + 哈希链**（防篡改） |

> **第 3 条是架构约束**：不许在小车上再起一堆节点。
> 小车只多一个订阅者，所有"看/调/记"都在主机完成。

## 2. 任务分解

### 2.1 裁判系统适配器

| 项 | 要求 |
| :-- | :-- |
| 文件 | `referee_bridge.py` |
| 订阅 | `/referee/cmd`（指令） |
| 发布 | `/referee/status`（我方状态） |
| 解析 | 倒计时、当前阶段、犯规记录、加罚时间 |
| 推送 | **实时推给仪表盘（M5-2）与状态机（M5-1）** |
| 模拟 | 本地键盘：`S`=START、`P`=PAUSE、`R`=RESUME、`E`=STOP（便于练习） |

**必须回答**：

- 收到 `PAUSE` 时，**正在跑的导航**怎么办？（取消？挂起？）状态机要**原子级暂停**
- 收到 `STOP` 与 `PENALTY` 的区别是什么？（前者结束，后者继续但记录）
- 裁判**超时未发指令**怎么办？（比如倒计时结束但没收到 `STOP`）
- 你的状态回报**多久发一次**？（事件驱动还是周期？）

### 2.2 多模态交互终端

**任务控制区**：

| 按钮 | 动作 |
| :-- | :-- |
| 启动任务 | 发 `/referee/start_cmd` 或调状态机 `start()` |
| 暂停 / 继续 | 发 `/task_pause` `/task_resume`；状态机**原子级暂停** |
| 跳过当前节点 | 标 `SKIPPED`，走 fallback |
| **紧急停车** | 大红按钮；见 §2.3 |

**参数/模型热切区**：

| 操作 | 实现 | 记录 |
| :-- | :-- | :-- |
| 切 `scene_*.yaml` | `ros2 param load` | 时间/旧值/新值/操作人/实验名 |
| 切感知模型 | 热加载 `model_path`（**不重启节点**） | 同上 |
| 调滑块（导航速度/感知频率/置信度阈值） | `ros2 param set` | 同上 |

> **"不重启节点"怎么验证**：现场会看**节点 PID 是否变化**、以及
> 参数是否**真的生效**（如改了置信度阈值，检测结果随之变化）。

**必须回答**：

- "热加载模型"具体怎么做？（感知节点要实现一个**服务**来换模型？
  还是靠参数回调？说清你的接口约定）
- 如果新模型**加载失败**，旧模型还在吗？（**必须能回滚**）
- 滑块拖动频繁时会不会把参数服务打爆？（要不要节流/去抖）

**多模态触发**：

| 方式 | 要求 |
| :-- | :-- |
| 语音 | **离线**唤醒词（如 `vosk` / `sherpa-onnx`）：开始/暂停/停车/求助 |
| 物理按键 | GPIO 或 USB HID 映射**相同动作**（不是另写一套逻辑） |

**必须回答**：

- 语音误识别会不会**误触发急停**？你怎么防？
- 物理按键与界面按钮**要不要走同一条命令通道**？为什么？

### 2.3 安全兜底（本题重点）

**紧急停车必须是多层的**，只发一条零速度**不够**：

| 层 | 动作 | 为什么需要 |
| :-- | :-- | :-- |
| ① 指令层 | 发零速度 `/cmd_vel` | 常规停车 |
| ② 话题层 | 发 `/emergency_stop`（小车端订阅） | 让底盘**自己**进入急停状态 |
| ③ 控制器层 | 触发底盘控制器的**软件急停**（如置使能位为 0） | 防止控制器超时后又恢复运动 |
| ④ 记录层 | 写黑匣子 + 审计日志 | 事后追责/复盘 |

**必须回答**：

- 如果 `/cmd_vel` 的发布者**不止你的终端**（比如导航也在发），
  你发一条零速度够吗？（**不够**——要协调或抢占）
- 小车端的 `/emergency_stop` 订阅者收到后**应该做什么**？
  （提示：不能只发零速度，还要**锁住**直到复位）
- 急停后怎么**解除**？（不能自动恢复，必须手动确认）

**求助与复位**：

| 功能 | 行为 |
| :-- | :-- |
| 求助裁判 | 发 `/referee/help` + 语音播报「请求人工介入」 |
| 软复位 | 重新初始化状态机上下文、重发导航目标，**不重启节点** |
| 硬复位 | 全栈重启（**仅赛前/赛后可用，比赛中禁用**） |

**必须回答**：

- 软复位后，**旧的回调/定时器**会不会残留？（要能说清怎么清理）
- 硬复位**怎么保证比赛中调不到**？（界面上禁用？还是需要二次确认+权限？）

### 2.4 审计日志与合规

**格式**：`audit_log_<date>.jsonl`（每行一条 JSON）

```json
{"ts":"2026-09-22T15:30:12.345","op":"MODEL_SWITCH","from":"yolov8n_fp32","to":"yolov8n_int8","source":"ui","user":"operator","result":"ok","prev_hash":"a1b2..."}
{"ts":"2026-09-22T15:30:45.001","op":"EMERGENCY_STOP","source":"physical_button","user":"operator","result":"ok","prev_hash":"c3d4..."}
```

**要求**：

| 项 | 说明 |
| :-- | :-- |
| 只追加 | 不允许修改历史行 |
| **哈希链** | 每行含前一行哈希，篡改任一行会导致后续校验失败 |
| 完整性校验 | 提供 `verify_audit.py` 能验证整条链 |
| 覆盖所有操作 | 含**自动触发**的降级、急停（不只是人工点击） |

**必须回答**：

- 哈希链里**第一条**的 `prev_hash` 是什么？
- 如果有人**删掉最后一行**，你的校验能不能发现？想清楚你的方案能防什么、不能防什么。
- 日志里的 `user` 从哪来？（现场只有一台主机，怎么区分操作人？）

## 3. 现场流程（约 20 分钟）

| 环节 | 内容 | 时间 |
| :-- | :-- | :--: |
| 启动终端 | 看界面是否集成全部功能（不许开新终端） | 3 min |
| **完整赛制演练** | 裁判发 `START` → 倒计时 → 状态机启动 → 仪表盘同步 | 5 min |
| **热切验证** | 切模型/参数 → 确认**PID 未变**且**生效**，`switch_log.csv` 有记录 | 4 min |
| **故障联动** | 拔相机 → 看门狗降级 → 终端告警 + 语音播报 | 3 min |
| **急停演练** | 按物理急停 → 零速度 + 黑匣子 + 审计 + 裁判收到 `FAULT` | 3 min |
| 审计校验 | 现场跑 `verify_audit.py`，再**手改一行**看是否能检出 | 2 min |

### 热切验证的具体做法

考官会：

1. 记录感知节点**PID**
2. 在终端点「切模型 → yolov8n_int8」
3. 确认 **PID 没变**、模型确实换了（看日志或性能变化）
4. 检查 `switch_log.csv` 与 `audit_log` 都有这条记录

### 急停验证的具体做法

考官会：

1. 让车**正在运动**
2. 按**物理急停按钮**
3. 确认：底盘停住、**不再自动恢复**、审计写入 `EMERGENCY_STOP`、裁判端收到 `FAULT`
4. 再确认**误触保护**（语音误识别不会直接急停）

## 5. 明确禁止

- 禁止急停只发一条零速度（必须**分层**：指令 + 话题 + 控制器 + 记录）
- 禁止急停后**自动恢复**（必须手动复位）
- 禁止硬复位能在比赛中触发（要有防护）
- 禁止"热切"其实是**重启节点**（现场核对 PID）
- 禁止模型切换**没有回滚**（新模型加载失败必须保住旧的）
- 禁止审计日志可编辑（只追加 + 哈希链）
- 禁止语音直接触发急停而无确认（误识别会导致比赛中断）
- 禁止在小车端加额外进程（题面要求只多一个订阅者）
