> **难度**：★★★
> **综合考察**：深度学习基础知识、数据工程、训练与调参、评估与归因、CPU 部署与性能分析
> **本题分值**：30 分
> **题目来源**：`创意组一轮考核.md` §M2-3
> **形式**：自行采数据、自行标注、自行训练；现场带模型与文档，**用你自己的物料与数据实测**

## 0. 这道题在考什么

赛项要识别 6 类物料，规则要求用深度学习。你**从零**走完一遍：
采数据 → 标注 → 训练 → 评估 → CPU 部署 → 实时演示。

评分重心不在"mAP 多高"，而在：

1. **闭环完整性**——每一环都有产物、可复现
2. **评估与归因**——能不能说出模型**为什么**在这类样本上翻车
3. **性能分析**——部署后耗时花在哪，你知不知道

## 2. 任务定义

**检测（不是分类）**：输入一帧图像，输出图像中**所有目标**的
`[类别, 置信度, xmin, ymin, xmax, ymax]`。

**6 类物料**（自己定具体物体，写进文档；**物料自带**，现场要能摆出至少 4 类）：

| 类别 | 示例 | 建议难度点 |
| :-- | :-- | :-- |
| class_0 | 药盒 | 长方体，正面有字 |
| class_1 | 医疗器械 | 形状不规则 |
| class_2 | 交通标志 | 颜色鲜艳，圆形为主 |
| class_3 | 水果-苹果 | 颜色与其他类易混 |
| class_4 | 水果-香蕉 | 细长形，姿态变化大 |
| class_5 | 背景物 | **易与某类混淆的干扰物**（自定，用于制造评估话题） |

> 类别可以换成你手头方便采的物体，但必须**恰好 6 类**、
> 且**至少有 1 对类别是天然易混的**（颜色/形状接近）——这是本题评估环节的前提。

---

## 3. 数据采集与标注（任务完成 40 中的 10 分）

| 项 | 要求 |
| :-- | :-- |
| 数量 | **每类 ≥120 张有效图**（总 ≥720 张）；不足时用**同分布**增强补足，但原始采集数必须如实报告 |
| 多样性 | 至少覆盖：不同背景（≥3 种）、不同光照（强/弱/逆光）、不同距离与角度、**部分遮挡**样本 |
| 划分 | train / val / test = 7 : 2 : 1，**按场景划分**（同一批次同背景的图不许跨集合），防止信息泄漏 |
| 标注 | bbox 精确到目标边缘 ±3px；工具自选（labelImg / CVAT / Roboflow 均可） |
| 格式 | YOLO txt 或 COCO json，**在文档里写明格式与类别 ID 映射** |

**必做的一项工程实验**（写进文档）：

- 统计**类别数量分布**，画出柱状图（matplotlib 或 PIL 均可）
- 如果某类样本明显少（长尾），说明你打算怎么处理（过采样 / 增强 / 加权 loss），
  **并实测处理前后的 mAP 差**

> **信息泄漏是本题最常被抓的点**：同一张背景上连拍的图若分属 train 与 test，
> mAP 会虚高。现场会抽查你的划分逻辑。

## 4. 训练（任务完成 40 中的 8 分）

| 项 | 要求 |
| :-- | :-- |
| 框架 | PyTorch / TensorFlow / PaddlePaddle 任一；**必须能在 CPU 上完成推理** |
| 模型 | 可用现成架构（YOLOv5n / SSD-Lite / NanoDet 等）或自研小模型；**用预训练权重必须写明来源与 license** |
| 训练记录 | loss 曲线、学习率策略、epoch 数、增强方式，全部留档 |
| 复现 | 给出**一键训练命令**（脚本 + 依赖清单），现场可能要求重跑少量 epoch 验证 |

**文档必须回答**：

- 为什么选这个模型？（参数量、CPU 推理速度、精度的权衡）
- 训练时用过哪些增强？哪些**不该**用（比如对颜色敏感的任务做了大幅色相抖动）？
- 过拟合/欠拟合你是怎么判断的？给出了什么证据（曲线）？

> **资源提醒**：现场环境无 GPU。训练可以**在自有 GPU 机器上做**，
> 但提交的模型必须**CPU 可推理**（导出 ONNX 或直接 PyTorch CPU），
> 并在文档中给出 CPU 单帧推理耗时。

## 5. 评估与归因（任务完成 40 中的 11 分，单项最重）

### 4.1 指标（缺一扣分）

在 **test 集**上报告：`mAP@0.5`、`mAP@0.5:0.95`、各类 **Precision / Recall / F1**、**混淆矩阵**。

> 计算脚本可以自己写或用现成库，但**必须能解释**：
> TP/FP 怎么判定（IoU 阈值 + 类别一致）、mAP@0.5 与 @0.95 的区别、
> 为什么小目标的 AP 天然偏低。

### 4.2 归因（本题的灵魂）

对 test 集做**错误分析**，至少覆盖：

| 分析 | 要写清 |
| :-- | :-- |
| 最容易混的一对类 | 是哪两类？混淆矩阵里体现为多少？**看错分的样本图**，说出原因（颜色？形状？背景？） |
| 最差的单类 | 它的 P 低还是 R 低？P 低说明什么（误检多，可能背景像它）；R 低说明什么（漏检多，可能样本少或遮挡） |
| 失败样本展示 | **至少 6 张**失败图，每张标注"为什么错"（不是"效果不好"） |
| 数据缺陷 | 回头看数据，哪些采集/标注问题直接导致了上面的错误 |

> **评估与归因占 8 分，是本题分值最高的单项**。
> 只报指标不做归因，这一项最多拿 2 分。
> 现场会**随机抽一张你贴的失败样本**，问你"这是什么问题、怎么改"。

## 6. CPU 部署与性能测试（任务完成 40 中的 7 分）

### 5.1 部署

- 导出 **ONNX**（推荐）或 TorchScript，用 `onnxruntime`（CPUExecutionProvider）推理
- 预处理必须与训练时**严格一致**（resize 方式、归一化均值方差、通道顺序）
  ——这是部署后精度掉点的第一大原因，文档要写清楚

### 5.2 性能数据（现场环境实测，别只报自己机器）

| 指标 | 说明 |
| :-- | :-- |
| FPS | 端到端（含读取与后处理），≥200 帧取平均 |
| 预处理耗时 | resize / 归一化 / HWC→CHW |
| 推理耗时 | 纯模型 forward |
| 后处理耗时 | 解码 + NMS |

**展示形式**：**耗时分布图**（饼图/柱状图）+ 数据表。
`matplotlib` 不可用时用 **PIL 画**（参考做法：把色块和文字画上去再存 png），
或直接输出 CSV + 文字直方图。

### 5.3 一致性验证（必做）

PyTorch 模型与 ONNX 模型在**同一批图**上的输出差异：
`max |Δbox|`、`max |Δconf|`。超过 1e-3 要解释（通常是预处理不一致）。

## 11. 常见追问

1. train/val/test 怎么划分的？**为什么按场景而不是随机**？
2. 你的 mAP@0.5 与 @0.95 差多少？这个差距大说明什么？
3. 混淆矩阵里最亮的那对类别，**翻 5 张错分图**给我讲讲为什么。
4. 某类 Precision 很低，你先怀疑数据还是模型？怎么验证？
5. 预处理训练和部署不一致会怎样？你怎么发现这种不一致？
6. NMS 的 IoU 阈值调高/调低分别会怎样？
7. 模型在 CPU 上 12 FPS，**瓶颈最可能在哪**？你的耗时分布图怎么证明？
8. 如果现场只有 100 张新图（新背景），你怎么快速提升这类场景的表现？
9. 数据里那对"天然易混"的类，你的标注有没有把边界划清楚？

## 12. 明确禁止

- 禁止只交模型不给数据（现场无法归因 = 评估项崩盘）
- 禁止 val 集调参、test 集只跑一次的"假流程"（test 必须只在最终报告时用）
- 禁止用 test 集 mAP 选模型
- 禁止标注工具直接生成的框不加人工核对（抽检会发现明显的框偏移）
- 禁止 CPU 推理用 GPU 版本库的算子（必须能在现场环境跑起来）
