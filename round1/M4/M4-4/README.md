# M4-4 ｜ 车与大脑之间的桥：上下位机协议

> **难度**：★★★★
> **综合考察**：协议设计、串口通信健壮性、CRC 校验、跨平台联调
> **本题分值权重**：40
> **题目来源**：`创意组一轮考核.md` §M4-4
> **形式**：自备开发板 + Linux 主机（或虚拟机）；现场带两端代码与协议文档，**考官会做破坏性测试**

---

## 0. 这道题在考什么

嵌入式链路里**最容易在比赛现场崩掉**的一环：**串口通信**。

它崩的方式很有特点：实验室好好的，赛场上线松一点、波特率被改、电机干扰一上来，
**帧就错位了**。如果你的协议没有帧同步与校验，表现就是"车突然乱动"或"完全没反应"。

本题考四件事：

1. **协议设计**——帧格式是否自洽、能否从任意错误中**重新同步**
2. **两端实现**——MCU 端与 Linux 端**独立**实现，靠文档对齐（不是靠一起调试凑）
3. **健壮性**——**三种破坏场景**下都不许死机，且**坏帧计数正确**
4. **联调能力**——现场改一端，另一端不改也能对上（**协议是契约**）

> 现场考点是第 3 条：考官会**故意改错波特率、插入脏字节、拔线再插回**。
> "死机了"或"坏帧数不对"都算失败。

## 1. 硬性要求

| # | 要求 | 说明 |
| :-- | :-- | :-- |
| 1 | **二进制帧协议** | 帧头 + 长度 + 消息 ID + 载荷 + **CRC**；**必须写明字节序** |
| 2 | **协议文档 v1.0** | 独立文档，含帧格式表、消息 ID 表、字段单位、示例帧（十六进制） |
| 3 | **MCU 端** | 解析上位机**速度指令帧**；按 **50ms** 回报**状态帧**（轮速/姿态/心跳计数） |
| 4 | **CRC 校验** | 校验失败的帧**丢弃并计数**（计数要能被上位机读到） |
| 5 | **Linux 端工具** | **C 或 C++**（不是 Python）；读取并解析下位机数据；能下发指令 |
| 6 | **三种破坏场景** | 改错波特率 / 插脏字节 / 拔线再插，**均不得死机**，坏帧计数正确 |
| 7 | **从任意状态重同步** | 收到半截帧或错位数据后，能靠帧头重新对齐 |

> **第 7 条最容易被忽略**：如果接收逻辑假设"每次读到的都是完整帧"，
> 一旦错位就永远对不上了——现场插脏字节必现。

## 2. 任务分解

### 2.1 设计协议（写文档 v1.0）

**帧格式**（推荐结构，可自定但要完整）：

| 字段 | 长度 | 说明 |
| :-- | :-- | :-- |
| 帧头 | 2 B | 固定魔数（如 `0xAA 0x55`），用于重同步 |
| 长度 | 1 B | **载荷长度**（或整帧长度，要写明） |
| 消息 ID | 1 B | 区分消息类型（见下表） |
| 序列号 | 1 B | 可选，用于检测丢帧 |
| 载荷 | N B | 具体内容 |
| CRC16 | 2 B | 覆盖范围要写明（帧头到载荷？还是不含帧头？） |

**消息 ID 表**（至少这两条）：

| ID | 方向 | 名称 | 载荷 | 频率 |
| :-- | :-- | :-- | :-- | :-- |
| 0x01 | 上位机 → MCU | 速度指令 | `left_rpm(int16)`, `right_rpm(int16)` | 按需 |
| 0x02 | MCU → 上位机 | 状态回报 | `left_rpm`, `right_rpm`, `pitch`, `heartbeat`, `bad_frame_cnt` | **50ms** |

**文档必须写明**：

| 项 | 要求 |
| :-- | :-- |
| 字节序 | 大端 **还是** 小端（**必须明确**，两端不一致就是经典 bug） |
| 有符号数 | `int16` 负数怎么表示（补码） |
| 浮点 | 角度用 `int16`（×100 定点）还是 `float`？**两者都要写明**，定点更适合串口 |
| CRC 参数 | 多项式、初值、是否反转输入/输出（如 CRC-16/MODBUS） |
| CRC 覆盖范围 | 从哪个字节算到哪个字节 |
| 示例帧 | **给出至少 2 条真实字节序列**（十六进制），并标注每个字段 |

**示例帧长什么样**（下面是**出题人给出的参考帧**，供你对照格式；
**你的协议可以不同**，但必须同样完整且能被独立复算）：

```
速度指令帧（上位机 → MCU，左右轮各 60 r/min）

AA 55 04 01 3C 00 3C 00 EE 1D
│     │  │  └────┬────┘ └──┬─┘
│     │  │       │         └─ CRC16（小端）
│     │  │       └─────────── 载荷: int16 左轮 / int16 右轮（小端）
│     │  └─────────────────── 消息 ID = 0x01（速度指令）
│     └────────────────────── 载荷长度 = 4 字节
└──────────────────────────── 帧头 0xAA 0x55
```

- 字节序：**小端**
- CRC：**CRC-16/MODBUS**（多项式 `0xA001` 反射式、初值 `0xFFFF`），
  **覆盖范围 = 帧头到载荷**（不含 CRC 本身）
- 角度类字段建议用 **定点**（`int16`，单位 0.01°，即 ×100），比 `float` 更适合串口

> **自检**：把你自己的示例帧丢给一个**独立脚本**（或用在线 CRC 计算器）核一遍 CRC。
> 现场考官会这么做——**文档里的示例帧必须能被复算出来**。

**必须回答**：

- 为什么**不能只用和校验**（checksum）？（CRC 的检错能力在哪）
- 帧头 `0xAA 0x55` 如果出现在**载荷里**会怎样？你怎么处理？（这是协议设计的关键）
- 长度字段如果被干扰成很大的值，你的接收缓存会怎样？（**要有上限保护**）

### 2.2 MCU 端实现

| 项 | 要求 |
| :-- | :-- |
| 接收 | 中断/DMA 收字节 → 环形缓冲 → **状态机解析**（不要在主循环里 `HAL_UART_Receive` 死等） |
| 解析 | 逐字节喂状态机；校验失败**丢弃并计数** |
| 超时 | 帧内字节间隔超时（如 >50ms）→ 判定帧损坏，回到找帧头状态 |
| 发送 | 每 **50ms** 发一帧状态（用定时器，不许 `delay`） |
| 计数 | `bad_frame_cnt`（CRC 失败）、`timeout_cnt`、`overflow_cnt` 都要能上报 |
| 指令 | 收到速度指令后**实际驱动电机**（可复用 M4-3 的速度环） |

**状态机建议**（这是健壮性的核心）：

```
WAIT_HEAD1 -> WAIT_HEAD2 -> WAIT_LEN -> WAIT_ID -> WAIT_PAYLOAD -> WAIT_CRC -> 校验
     ^                                                                          |
     +------------------- 任何异常都回到这里重同步 -----------------------------+
```

**必须回答**：

- 为什么用**环形缓冲 + 状态机**，而不是"读满一帧再解析"？
- 如果上位机**发得比你处理得快**，缓冲满了怎么办？（丢最旧还是丢最新？理由）
- `bad_frame_cnt` 什么时候清零？（建议不清零，或只在收到明确命令时清零）

### 2.3 Linux 端 C/C++ 工具

| 项 | 要求 |
| :-- | :-- |
| 语言 | **C 或 C++**（题面明确要求，不用 Python） |
| 打开串口 | `termios` 配置：波特率、8N1、**原始模式（raw）**、**禁用回显与信号** |
| 读取 | **非阻塞**或 `select`/`poll`（不许死等） |
| 解析 | 与 MCU 端**同样的状态机**（两端逻辑对称，便于验证） |
| 发送 | 能按指定频率下发速度指令 |
| 输出 | 终端实时显示状态（轮速/姿态/心跳/坏帧数）；**支持存 CSV** |
| 参数 | 串口设备、波特率**从命令行传**（不许写死） |

**必须处理**（Linux 串口特有）：

| 坑 | 处理方式 |
| :-- | :-- |
| 串口默认是"终端模式"，会把 `0x0A` 等当换行处理 | 必须 `cfmakeraw()` |
| `Ctrl-C` 会往串口发信号字符 | 要屏蔽或忽略 |
| 拔线后 `read()` 返回什么 | 返回 0 或 -1，**不能当死循环空转** |
| 插回后需要重新打开设备吗 | 说明你的处理（建议：检测到错误就重开） |

### 2.4 健壮性演示（本题核心）

**三种破坏场景**，每种都要：

1. 演示过程（现场）
2. **坏帧计数正确**（不是"大概不出错"）
3. 系统**不死机、不卡住**

| 场景 | 怎么造 | 预期行为 |
| :-- | :-- | :-- |
| **① 波特率被改错** | 把一端改成 9600（另一端仍 115200） | 收到全是垃圾 → **坏帧计数飞涨** → 但进程/固件**不崩** |
| **② 插入脏字节** | 在帧中间/帧头之间插入随机字节 | 状态机**重新同步**；下一个好帧仍能正确解析 |
| **③ 拔线再插回** | 运行中拔掉 USB-TTL，几秒后插回 | Linux 端不崩、不空转死循环；MCU 端继续发；插回后**恢复通信** |

**要求给出**：

- 每种场景下，**坏帧计数的变化**（前后对比数字）
- 场景 ② 的**关键验证**：插脏字节后，**好帧仍被正确处理**（不能"脏一次就永久失步"）
- 场景 ③ 的**恢复时间**（插回后多久恢复）

**必须回答**：

- 场景 ① 里，坏帧计数**应该**是多少？（本质上所有字节都是垃圾，为什么计数不会爆炸到无穷）
- 场景 ② 里，如果脏字节里**恰好含帧头**，会怎样？
- 场景 ③ 里，MCU 端**知不知道**上位机断开了？怎么知道？（提示：加超时检测）

## 3. 现场流程（约 25 分钟）

| 环节 | 内容 | 时间 |
| :-- | :-- | :--: |
| 协议检查 | 读文档 v1.0，抽查示例帧能否被独立解析（**手算 CRC**） | 5 min |
| 正常运行 | 两端联调，看 50ms 状态回报与指令响应 | 4 min |
| **破坏测试** | **考官现场做三种破坏**，看坏帧计数与是否死机 | 8 min |
| 交叉验证 | 考官改**一端**的字节序（或 CRC 范围），另一端**不改**——确认协议是契约 | 4 min |
| 追问 | 状态机设计、缓冲策略、重同步逻辑 | 4 min |

### 交叉验证的做法（重点）

考官会：

1. 拿你**文档里的示例帧**，用**独立脚本**解析一遍 → 验证文档与实现的**一致性**
2. 把 MCU 端**字节序改成反的**（或 CRC 覆盖范围改一格）→ 上位机应该**报坏帧**而不是"解析出乱码数值"

> 如果你的上位机在字节序错的情况下**还能解析出"看起来合理"的数值**，
> 说明你的校验覆盖面不足——这是设计缺陷。

## 5. 明确禁止

- 禁止用**文本协议**（题面要求二进制帧；文本无法覆盖 CRC 与重同步考点）
- 禁止不退化成"每帧开头对齐"的假设（必须能从任意错位恢复）
- 禁止 Linux 端用 Python（题面明确要求 C/C++）
- 禁止不做 `cfmakeraw()`（会把二进制数据当控制字符处理）
- 禁止长度字段无上限保护（脏字节会把缓冲写爆）
- 禁止坏帧计数"只增不清"却无法上报（现场要读数）
- 禁止两端字节序/CRC 范围不一致（现场交叉验证会暴露）
- 禁止拔线后进程空转死循环（CPU 打满且无法恢复）
